# 絲網印刷半調墨點 Halftone Studio

將 JPG / PNG 影像轉為絲網印刷用的二值半調墨點（黑墨白底）。

純 Python + NumPy 實作，**完全不依賴 GIMP 或任何外部影像軟體**。

**開發：Film Halftone（AI 協作開發）** — 程式碼與文件由 AI 輔助產生與維護。

## 核心概念

半調墨點有兩條互相獨立的軸，本程式分別控制：

### 1. 墨點位置 —— 「隨機網占比」

| 值 | 效果 |
|---|---|
| **0%** | 藍雜訊隨機顆粒，位置隨機但間距均勻（膠片顆粒感） |
| **50%** | 隨機與規則網格共存 |
| **100%** | 傳統有序墨點網格（AM 網屏） |

墨點位置由藍雜訊抖動決定，抖動幅度隨占比連續變化，因此兩種質感之間
是**無縫過渡**而非切換。

### 2. 墨點形狀 —— 「墨點形狀」

| 選項 | 說明 |
|---|---|
| 圓形 | 傳統圓點 |
| 方形 | 方形墨點 |
| **十字架** | 由水平臂與垂直臂兩個矩形的**聯集**構成，等值線就是乾淨的十字，四角留白 |
| **有機隨機（銀鹽顆粒）** | 每顆顆粒的輪廓都不相同，模擬膠片銀鹽晶體 |

> 形狀對**所有模式都有效** —— 不論墨點是排成規則網格還是隨機散開，
> 都套用同一套形狀距離度量。這是一個重要的設計決定：早期實作把形狀
> 綁在有序網上，導致純隨機模式下形狀參數完全失效。

> 十字架不是用圓角或疊加近似出來的。對單一矩形而言
> `max(|x|/a, |y|/b)` 的等值線恰好是該矩形，取兩個矩形的最小值即為
> 聯集，等值線因此正好是十字架。

## 參數說明

| 參數 | 範圍 | 作用 |
|---|---|---|
| 墨點形狀 | 四選一 | 圓形 / 方形 / 十字架 / 有機隨機 |
| 網屏線數 | 5–200 lpi | 每吋線數，決定墨點間距 |
| 網屏角度 | 0–90° | 網格排列角度 |
| 印刷寬度 | 20–1000 mm（可切換 mm / 寸） | 要印多寬，決定實際解析度 |
| 隨機墨點占比 | 0–100 % | 位置隨機程度 |
| 墨點不規則 | 0–1 | 墨點邊界的有機程度 |
| 墨點擴大 | 0–60 % | 墨點擴大補償，模擬油墨擴張 |
| 墨點大小範圍 | 0–100 % | 下限 = 最淡墨點，上限 = 最濃墨點 |
| 最小墨點過濾 | 0–5 mm | 小於此直徑的墨點直接捨棄留白；0 = 不過濾 |
| 藍雜訊尺寸 | 8–128 px | 隨機抖動的空間尺度 |
| 隨機種子 | 整數 | 同種子必定重現同一結果 |

### 參數已合併：只剩「印多寬」與「幾 lpi」

早期版本有「解析度」「墨點頻率」「顆粒粗細」三個滑桿，但它們只透過
**比值**影響同一件事（網格佔幾個像素）。實測證明只要比值相同，輸出
**逐像素完全相同**：

| 解析度 | 墨點頻率 | 網格像素 | 輸出 |
|---|---|---|---|
| 300 dpi | 40 lpi | 7.5 → 8 | 基準 |
| 600 dpi | 80 lpi | 7.5 → 8 | **逐像素相同** |
| 150 dpi | 20 lpi | 7.5 → 8 | **逐像素相同** |

而且解析度不會寫進輸出檔（中繼資料一律抹除），下游根本無從得知。
因此改成只填「印多寬」，解析度由畫面推導並只讀顯示：

```
實際解析度 = 圖寬(px) ÷ (印刷寬(mm) ÷ 25.4)
網格像素   = 實際解析度 ÷ 網屏線數
```

4500 px 寬的影像印六寸（152.4 mm）、40 lpi：

| 項目 | 數值 |
|---|---|
| 實際解析度 | 750 dpi |
| 墨點間距 | 0.635 mm（19 px） |
| 中值墨點直徑（50 % 網調） | 0.507 mm（15.0 px） |

這些數值會即時顯示在「印刷尺寸」區。最小墨點若換算後不足 1.5 px，
會提示「印不出來」。

### 墨點大小範圍：0 % 紙白 ~ 100 % 密實

兩個把手的範圍滑桿，直接控制墨量：

```
下限 lo ──────────── 上限 hi
紙白無點          完全密實填充
```

**`lo = 0` 讓純白區完全不下墨**，這解決了一個實際問題：舊版的
「最小墨點／最大墨點」預設 0.03 / 0.95，會**強迫純白區也印出 4.9 % 墨量**，
高光因此出現一堆只有一兩個像素的碎點，在絲印上完全沒有意義。

> 舊版那兩個參數夾在**亮度**上（白 = 1），名稱與作用剛好相反：
> `min_dot` 實際決定黑區最濃墨點、`max_dot` 決定白區最淡墨點。
> 現在改以墨量表示，`t = clip(t, 1 - hi, 1 - lo)`，名實相符。

### 最小墨點過濾：小於門檻的墨點直接捨棄

單位是**毫米**（圓形墨點直徑），`0 = 不過濾`。

這個控制項與「墨點大小範圍」**方向相反**：

| | 作用 |
|---|---|
| 墨點大小範圍（下限） | 把墨點**撐大**到指定比例 —— 寧可多印，不可少印 |
| **最小墨點過濾** | 把過小的墨點**整個丟掉、完全留白** —— 寧可留白，不可亂印 |

實測門檻精確（40 lpi、間距 0.635 mm、90 % 亮度區，墨點直徑 0.2419 mm）：

| 門檻 | 該區上墨率 |
|---|---|
| 0.20 / 0.23 / 0.24 mm | 0.1140（不影響） |
| **0.25 mm** | **0.0000（全部留白）** |

過濾在演算中的位置是**夾限之後**，因此它是最終裁決者：即使把下限
調到 30 %，只要撐大後的墨點仍小於門檻，照樣不會印出來。

門檻換算：`面積比例 = π × (門檻mm ÷ 間距mm)² ÷ 4`。若門檻已達網點
間距，整張會變成全白，介面會即時警告。

## 中繼資料處理

**讀入時只取可見像素資料。** 程式會依 EXIF Orientation 轉正影像（否則顯示方向會錯），
但相機型號、拍攝時間、版權、GPS、ICC 描述檔、JPEG 註解、內嵌縮圖等一律丟棄，
絕不帶入處理流程。

**輸出時另存新檔。** 原始檔案完全不會被修改，輸出檔案只寫入像素資料，
不含任何 EXIF 或文字區塊。

驗證方式：

```powershell
.venv\Scripts\python.exe tests\check_meta.py
```

實測結果：

| 項目 | 來源 | 輸出 PNG |
|---|---|---|
| EXIF 標記 | 7 個（含相機、版權、時間） | **0** |
| JPEG 註解 | 有 | **無** |
| 其他中繼資料 | DPI 等 | **無** |
| 像素 | — | **與計算結果完全一致（無損）** |

### 輸出格式

| 格式 | 無損 | 建議 |
|---|---|---|
| **PNG** | 是 | ✅ 實際製版用 |
| JPG | 否 | 僅供快速分享或預覽 |

> **PNG 以 1-bit 雙色輸出。** 半調結果本來就是純黑白，沒有任何灰階，
> 用 8 位元灰階只是浪費空間。1-bit 檔案體積最小，且讀回後與計算結果
> **逐像素相同**（實測通過）。輸出完成訊息會標明實際位元深度。
>
> **JPG 是有損壓縮。** 純黑白的墨點邊緣存成 JPG 後會出現灰階雜訊：
> 實測二值結果讀回後從 2 種灰階變成 4 種。
> 程式已用最高畫質（quality=100、4:4:4 無色度抽樣）把失真降到最低，
> 匯出前也會再次確認，但若要拿去製版請務必用 PNG。
>
> JPG 檔案中殘留的 `jfif_density` / `jfif_unit` / `jfif_version`
> 是 JFIF 格式的強制結構（每個合規 JPEG 都必須有），無法移除；
> 其中 `jfif_unit=0` 代表「無單位、無解析度」，不構成解析度資訊。

## 預覽與產出的一致性

這是本專案最容易出錯、也最重要的一點。

### 墨點尺寸是以「像素」計算的

墨點大小 = 解析度 ÷ 墨點頻率，單位是像素。整圖預覽為了效能必須縮圖，
若直接沿用原本解析度，墨點相對整張圖會被放大數倍 —— 預覽與實際產出
完全對不上。因此預覽時解析度會**依縮圖比例同步縮小**，兩者尺度才一致。

墨點若小於約 3 px 已接近取樣極限，此時維持 3 px，改由細節放大窗格負責。

### 點擊定位：縮圖座標 ≠ 全解析度座標

總覽顯示縮圖，但裁切框與細節窗格都用**全解析度**座標。
若直接沿用縮圖座標，24MP 影像會有 23%–58% 的定位誤差 ——
點右下角，實際落在全圖 23% 的位置。現已做兩段換算
（視窗 → 縮圖 → 原圖），實測誤差 0.1%–0.3%。

### 細節放大視窗：所見即所得

獨立的浮動視窗，疊在主預覽右下角，以**全解析度**計算指定區域：

- 在總覽圖上點擊即可移動取樣位置，框線會顯示目前範圍
- 可選取樣尺寸（640×480 / 960×720 / 1400×1050）與放大倍率（1:1 / 2 倍 / 3 倍）
- **輸出與匯出檔逐像素相符** —— 實測差異 71 / 307200 像素（0.023%），
  差異來自歸一化直方圖的分帶量化，肉眼與製版皆無影響
- **右下角嚴格角對角錨定**在主預覽區（誤差 0px）。主視窗拖曳移動、
  縮放，或拖曳分隔線改變預覽寬度時都自動跟隨；
  連續拖曳 40 步、連續縮放 20 次實測偏移皆為 **0px**
- 位置固定，不可拖曳移動；左上角控制點可往左上拉大
  （右下角固定，尺寸永遠不會超出主視窗）
- 拖曳分隔線改變預覽寬度後仍精確對齊
- `×` 關閉，`檢視 → 細節放大視窗`（Ctrl+D）開關，兩者狀態同步

網格錨定在「整張原圖」的座標系（`halftone(..., origin=, full_shape=)`），
所以單獨計算某一區域與整圖計算的結果一致。

### 總覽的繪製不使用 QLabel 的內建縮圖

`QLabel` 在圖片大於控件時會**自行再縮放一次**，而 `pixmap()` 回傳的仍是
縮放前的原圖 —— 畫面位置、框線位置、點擊換算於是各用各的座標，
框線就會明顯偏移，放大時尤其嚴重。

現在影像由 `paintEvent` 自行繪製，繪製矩形（`_drawn`）是唯一依據，
三者必然一致。實測框線中心誤差 **0.2px**。放大時控件會長到影像大小，
由外層捲動區提供捲軸。

## 完全離線，不會彈出終端視窗

程式**沒有任何網路功能**：原始碼不含 `socket` / `urllib` / `requests` / `http`，
執行檔的 PE 子系統為 `WINDOWS_GUI`（結構上就不附帶主控台），
實測啟動與執行期間 TCP 連線為 **0 筆**。

早期版本為了清除 `%TEMP%\_MEIxxxxx` 暫存目錄，在啟動時執行

```
cmd /c "ping -n 4 127.0.0.1 >nul & rmdir /s /q <_MEIPASS>"
```

那個 ping 打的是**本機回送位址**，封包不會離開電腦，但使用者的畫面上
會跳出黑色終端視窗並看到連續回應，極易誤以為程式在連網。
加上 `CREATE_NO_WINDOW` 與 `DETACHED_PROCESS` 互相衝突（MSDN 註明
兩者不可併用），視窗仍會被開出來。

現在改為**啟動時自行清理**（`main.purge_stale_meipass()`）：

- 不啟動任何子行程，自然沒有終端視窗
- 只刪除**超過 24 小時**且刪得掉的 `_MEI*` 目錄；使用者若同時開著
  另一個實例，其目錄必然不到 24 小時，不會被誤刪
- 刪不掉（仍被占用）就安靜略過，任何失敗都不影響啟動
- 本行程自己的 `_MEIPASS` 絕不碰

正常關閉時 bootloader 本來就會自行清除，實測點擊 X 後 **0.1 秒**退出、
殘留行程 0、暫存目錄歸零；強制結束留下的垃圾，下一次啟動就會回收。

驗證方式：

```powershell
.venv\Scripts\python.exe tests\check_mei.py
```

## 演算法原理

採用 **AM（振幅調變）網屏**模型：先計算每個像素到最近墨點中心的「形狀距離」，
再把距離場以直方圖 CDF 歸一化成 0–1 均勻分佈的門檻，最後與暗度比較決定上墨。

- 位置與形狀是**兩條獨立的軸**：藍雜訊式的隨機抖動決定墨點中心偏移，
  形狀距離場對所有模式一致生效
- **整圖絕對座標計算，完全不切磚平鋪**。早期實作把門檻場切成小磚重複貼滿全圖，
  24MP 影像上同一組隨機值重複兩萬多次，宏觀看又變回規則墨點且磚塊邊界有接縫
- 歸一化是必要的：墨點抖動後會互相重疊，只用「面積正比於距離平方」會把
  重疊部分重複計入，實測暗部上墨率最多低估 30%

實測密度還原誤差 **< 0.05%**（四種模式、全部形狀、全灰階範圍）。

### 效能

24MP（6000×4000）匯出約 5 秒（半調 4.2 秒 + 寫 1-bit PNG 0.8 秒），
分帶處理記憶體水位固定。預覽、匯出都在背景執行緒，介面不凍結。

### 演算法原理

再依此距離排名化為 0–1 均勻分佈的門檻場，最後與灰階比較決定上墨。

門檻場均勻分佈是密度能正確還原的關鍵 —— 任何區塊的上墨率會自動等於該區塊的
暗度，不需要任何全域密度校準。實測四種模式、全部形狀的密度誤差皆在 3% 以內。

匯出時才處理全解析度。

## 開發注意事項

- **背景執行緒**：預覽採 `QThreadPool` + `QRunnable`。不要改成在背景執行緒中
  直接呼叫 `@Slot` 方法 —— 那會在「呼叫者」執行緒執行，而非物件所屬執行緒。
- **亂數溢出**：`np.uint64` 標量乘法會拋出 overflow 警告，陣列乘法則靜默回繞。
  雜湊運算必須全程使用陣列。
- **浮點型別**：float32 與 float64 混合運算可能造成數值上溢，界線運算須明確指定。
